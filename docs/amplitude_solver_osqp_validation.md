# OSQP vs enumeration for the Application1 joint amplitude fit

Date: 2026-10-01. Scope: the **joint amplitude fit only**. This document does
not validate source recovery, initialization quality, or the 8–10-source
problems the new solver is intended to unlock.

Reproduce with:

```
PY="python3"
cd "Applications/Application1/test scripts" && "$PY" test_amplitude_solver_osqp.py
```

Machine-readable results:
`Applications/Application1/output/amplitude_solver_validation/amplitude_solver_comparison.json`
(gitignored; regenerated by the command above).

## The problem both solvers are given

For fixed source centers the variable-projected amplitude fit is

```
min_{A_min <= a <= A_max}   0.5 a^T H a - a^T h
H[i,j] = <du_ci, du_cj>_obs + lambda*delta_ij
h[i]   = <du_ci, u_d>_obs
```

in the repository's exact weighted observation/time inner product
(`sensitivity_initialization._ObsTraceContext`). Both solvers receive
byte-identical `H` and `h`, identical bounds, and the caller's `lambda` already
folded onto the diagonal. OSQP is given `P = H` (explicitly symmetrized),
`q = -h`, `A = I`, `l = A_min`, `u = A_max`.

### How an OSQP answer is accepted

`eps_abs = eps_rel = 1e-10`, `max_iter = 20000`, polish on. Acceptance is **not
decided by OSQP's status label**, which measurement showed to be unreliable in
both directions on badly scaled Gram matrices: OSQP can report `solved` for a
point whose scaled box-KKT residual is ~1e-3, and `solved inaccurate` for a
point that is in fact optimal to ~1e-11 (because the requested tolerance was
deliberately tight). So:

1. the status must be `solved` or `solved inaccurate` — anything else
   (`maximum iterations reached`, `primal infeasible`, …) is rejected at once;
2. the iterate must be finite and within `1e-8` of the box, then it is clipped
   onto the box;
3. the scaled projected-gradient residual
   `‖a − P_[lo,hi](a − (Ha − h))‖_inf / max(1, ‖h‖_inf)` is computed
   independently and must be `<= 1e-7` (`OSQP_KKT_TOL`).

Step 3 is a **verification, not a repair**. A point that fails is rejected with
the measured residual and `cond(H)` in the message; nothing is patched,
re-solved with added regularization, or quietly handed to enumeration.

## Why OSQP is the default: cost by source count

Measured on this workstation, min-of-N per call (random SPD `H` of each size,
bounds `(0.1, 2.0)`):

| M | enumeration (`3^M` active sets) | osqp | speedup |
|---|---|---|---|
| 2 | `0.113` ms | `0.365` ms | `0.3x` |
| 3 | `0.387` ms | `0.363` ms | `1.1x` |
| 4 | `1.218` ms | `0.361` ms | `3.4x` |
| 5 | `3.815` ms | `0.348` ms | `11.0x` |
| 6 | `11.389` ms | `0.436` ms | `26.1x` |
| 7 | `36.025` ms | `0.377` ms | `95.5x` |
| 8 | `104.958` ms | `0.432` ms | `243.0x` |
| 9 | refused (`_ENUMERATION_MAX_SOURCES = 8`) | `0.454` ms | — |
| 10 | refused | `0.456` ms | — |

OSQP's cost is **flat in M**; enumeration's is `3^M`. The crossover is at M = 3.
At M = 2 OSQP costs `0.25` ms more per fit, which is immaterial against the
~1 s forward solves a beam initialization pays hundreds of times, so defaulting
to OSQP loses nothing at the current source counts while being the only one of
the two that reaches M > 8 at all. That is the rationale for the default: not a
gain at M = 2, but constant cost as M grows.

## Tolerances

| Tolerance | Value | Applies to |
|---|---|---|
| `TOL_OBJ_REL` | `1e-9` | relative difference in `0.5 a'Ha - a'h` |
| `TOL_TRACK_REL` | `1e-9` | relative difference in the full tracking objective |
| `TOL_BOUND_ABS` | `1e-12` | absolute bound violation of either solver |
| `TOL_OPT_REL` | `1e-8` | projected-gradient residual / `max(1, ‖h‖_inf)` |
| `TOL_AMP_ABS` | `1e-6` | amplitude difference — **gated only when `cond(H) <= 1e10`** |

The box-constrained first-order residual is
`‖a − P_[lo,hi](a − (Ha − h))‖_inf`, zero exactly at a KKT point.

## Measured results — non-unique amplitudes (`tfinal = 8 s`)

Same two centers, same weights, `tfinal` shortened so the upstream source's
plume has **not reached any measurement boundary**. Then `H[0,0] = 5.439e-23`,
`cond(H) = 1.984e+26`, and the objective is flat in `a_1` across the whole box,
so the minimizer in `a` is genuinely non-unique.

| Quantity | Value |
|---|---|
| `diag(H)` | `5.439e-23`, `1.079e+04` |
| `a` enumeration | `[1.1, 0.8499999999999999]` |
| `a` OSQP | `[0.1599984000195921, 0.8499999999999996]` |
| max `|Δa|` | `9.400e-01` — non-unique, reported, not gated |
| quadratic abs / rel diff | `9.095e-13` / `2.333e-16` |
| tracking `J` (enum / OSQP) | `2.391e-28` / `2.403e-23`, against `J(a=0) = 3.899e+03` |
| tracking `J` diff / `J(0)` | `6.164e-27` |
| scaled proj.-grad residual (enum / OSQP) | `0.000e+00` / `1.983e-16` |
| OSQP status | `solved` (50 iterations) |

The two solvers disagree by `0.94` in the unidentifiable amplitude while the
objective agrees to the last bit and both are first-order optimal. This is the
expected consequence of a rank-deficient `H`, not a solver defect — and it is
why the amplitude vector is not a gating criterion above `cond(H) = 1e10`.
It also means that **in a degenerate/unobservable configuration the two
selections can hand the downstream optimizer different (equally optimal)
starting amplitudes.**

## Solver-level checks

- **240 random convex box QPs**, `n ∈ [1, 6]`, 63 of them rank-deficient, bounds
  `(0.1, 2.0)`: worst relative objective difference `8.882e-16`, worst amplitude
  difference `6.692e-13`, worst OSQP bound violation `0`, worst scaled OSQP
  optimality residual `1.567e-12`.
- **Ill-conditioning stress batch** with the real `H = T'T`, `h = T'u_d`
  structure: `n ∈ [2, 10]`, per-response magnitudes spanning `1e-12 … 1e5`, 30%
  of trials with near-duplicate responses, so `cond(H)` reaches `inf`
  (numerically singular). 400 trials each, noiseless and at 1% noise:

  | | noiseless | 1% noise |
  |---|---|---|
  | refused (loudly) | 2 / 400 (0.5%) | 0 / 400 (0%) |
  | `cond(H)` of the refusals | `1.24e+29`, `7.38e+22` | — |
  | accepted scaled box-KKT residual, max / median | `1.604e-10` / `6.006e-12` | `8.248e-09` / `1.178e-12` |
  | worst objective gap vs enumeration (`n <= 8`) | `2.117e-10` | `1.007e-09` |

  Every accepted solution is first-order optimal and no worse than
  enumeration's objective. Both refusals are `maximum iterations reached` at
  `cond(H) >= 7e22`, and both name `--amplitude-solver enumeration`. The
  stress batch uses its own `STRESS_MAX_OBJECTIVE_GAP = 1e-7` rather than the
  production `1e-9`: at `cond(H) ~ 1e29` a `1e-9` relative gap is numerical
  noise. That threshold is ~60x above the worst gap measured over 4498 stress
  problems (`1.6e-09`; p99.9 `1.2e-09`, median `~1e-13`).

  **Residual risk accepted:** on problems this ill-conditioned OSQP refuses a
  small fraction of the time where enumeration would still answer. The refusal
  is loud and names the alternative, and no real Application1 configuration
  measured here reaches that regime (production `cond(H) = 73`; the
  unobservable `tfinal = 8 s` case at `cond = 2e26` solves in 50 iterations).
  An earlier draft with `eps = 1e-12` / `max_iter = 200000` and status-only
  acceptance refused `27/600` noiseless and `19/600` noisy cases; the verified-
  KKT gate plus `eps = 1e-10` is what reduced that to `2/400` and `0/400`.
- **Source-count limit is enumeration-specific.** `_ENUMERATION_MAX_SOURCES = 8`.
  OSQP solves `n = 8, 9, 10` in `0.38–0.40` ms with bound violation `0` and
  scaled optimality residual `1.5e-16 … 4.7e-16`; enumeration refuses `n = 9`
  and `n = 10` with an error naming `--amplitude-solver osqp`.
- **No silent fallback.** A hidden `osqp` import raises
  `SensitivityInitializationError` naming the `pip install` command,
  `tools/check_inverse_env.py`, and `--amplitude-solver enumeration`. A bad
  solver name is rejected by `validate_amplitude_solver` and by argparse.

## CLI / plumbing

- `--amplitude-solver` defaults to `osqp`; both choices parse; an invalid choice
  exits non-zero with argparse's `invalid choice` before any solve.
- With a spy on `_solve_box_qp`, a tiny two-candidate initialization (centers
  fixed, `tfinal = 8 s`, refinement + pair refinement + re-selection all on)
  performs **15 joint amplitude fits** and every one of them uses the requested
  solver, for both selections. The selection is recorded in the initializer
  extras and in `sensitivity_init_summary.json` under
  `options.amplitude_solver`. Both selections place **identical centers**
  (max diff `0.0` m); the `1.257` amplitude difference in that run is the
  `tfinal = 8 s` unidentifiable case above.

## Regression

Existing suites re-run unchanged with the new default: `test_sensitivity_scoring.py`
(12/12), `test_three_source_generalization.py` (all checks). `_solve_box_qp`'s own
default stays `enumeration`, so the existing diagnostic scripts that call it
directly are byte-for-byte unchanged and need no OSQP install.

## Verdict

The comparison and integration checks pass, so **OSQP is now Application1's
default joint amplitude solver** (`DEFAULT_AMPLITUDE_SOLVER = "osqp"`), with
`--amplitude-solver enumeration` retained as an explicitly selectable exact
reference.

**This validates the joint amplitude fit at M = 2 only.** It says nothing about
8–10-source *recovery*: the `n = 8, 9, 10` checks above are synthetic QPs, and
no 8–10-source PDE case has been run.

## Notes

- OSQP's internal ADMM `sigma` parameter is part of the algorithm, not a change
  to `H`; the polish step solves the exact KKT system of the submitted problem.
  No regularization is added to `H` or `h` by either solver.
- `solved inaccurate` is an accepted STATUS but not an accepted ANSWER: it
  still has to pass the independent box-KKT check above, as does `solved`.
- OSQP 1.1.3 writes polish notes to C-level stdout regardless of
  `verbose=False`; they are muted at the file-descriptor level
  (`OSQP_SUPPRESS_SOLVER_STDOUT`), while status/iteration count are read
  programmatically and surfaced in any error.
- Environment: Python 3.13.5, numpy 2.5.2, scipy 1.18.1, osqp 1.1.3.
